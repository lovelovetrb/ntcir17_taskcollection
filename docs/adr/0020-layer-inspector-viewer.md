# ADR-0020: 層ごとの検索結果を読むビューアを Streamlit で作る

- Status: Accepted
- Date: 2026-09-14

## 決定

浅い層と深い層で得意なトピックが分かれる理由を、モデルが実際に受け取ったクエリと文書を
読んで確かめるためのビューアを、`sandbox/layer_inspector/` に Streamlit アプリとして作る。

### 起動の流れ

エントリポイントは Streamlit アプリの 1 つだけとする。表示に要るものは結果ファイルに
書き出しておき、アプリはそれを読んで表示する。

```
アプリを起動する
  ├ 結果ファイルがない → 結果ファイルを作る
  └ 結果ファイルを読んで表示する
```

結果ファイルは次の順で作る。

```
1. layer-sweep の記録から、トピック・層ごとの指標を読む
2. 浅い層 (1・2) の最良と深い層 (11・12) の最良の nDCG@1000 の差でトピックを並べ、
   両端から 5 件ずつ選ぶ
3. 選んだトピックについて、両側の最良の層で検索し直す
4. 検索結果の上位 10 件と、適合文書の上位 5 件・下位 5 件を取り出し、
   両方の層での順位と判定を付ける
5. クエリと文書を 512 トークンで切り詰めて decode する
6. 結果ファイルに書き出す
```

順位は実験と同じ経路 (`build_search_vectors` → `rank_documents`) で求める。

### 表示するテキスト

モデルに入力されたものを表示する。クエリ (`query_text`、トピックの題名) と文書
(`document_text`、題名 + 空白 + 抄録) を、エンコードと同じトークナイザで 512 トークンに
切り詰めて (ADR-0004) トークン列にし、それを decode した文字列をそのまま表示する。
特殊トークンは取り除かず、`[CLS]`・`[SEP]`・`[UNK]` も表示する。

対象モデルのトークナイザは MeCab で単語に分けたあと WordPiece で分けるため、decode した
文字列は元の文章と次の点で異なる。

```
単語の間に空白が入る        統計 的 言語 モデル を 用い た
NFKC 正規化がかかる         ＡＢＣ → ABC、① → 1、㈱ → (株)
語彙にない文字は [UNK] になる  𠮷野家と🍣の検索 → [CLS] [UNK] 野家 と [UNK] の 検索 [SEP]
```

### 画面構成

画面を左右に 2 分割し、左側をさらに 2 列に分ける。

```
左側・1 列目   浅い層が優位なトピック 5 件 / 深い層が優位なトピック 5 件
左側・2 列目   選んだトピックの指標 / 検索結果の上位 10 件 /
              適合文書の上位 5 件 / 適合文書の下位 5 件
右側           順位・判定・文書 ID・クエリ / 文書
```

画面のモック (数値と文章はダミー):
<https://claude.ai/code/artifact/6bd9a2a7-cc70-472b-a34c-528a4f9617c8>

左側の行を選ぶと、右側の表示が切り替わる。nDCG@1000 などの指標は表に入れる。
文書の表には、検索した層での順位と反対側の層での順位を並べる。

適合文書が 10 件以下のトピックでは、上位と下位の表が重ならないように分ける。
順位の高い順に並べた適合文書のうち、先頭 5 件を上位の表に、残りの末尾 5 件までを
下位の表に入れる。

### 依存とテスト

`streamlit` はパッケージ本体の `dependencies` ではなく、dependency group `sandbox` に
入れる。仮想環境はプロジェクトの 1 つを使う。

コードとテストは `sandbox/layer_inspector/` に置く。Streamlit に依存しない処理に
テストを書き、画面にはテストを書かない。

テストは `tests` と同じ pytest の実行で動かす。`pyproject.toml` の `testpaths` に
`sandbox` を加え、`make test`・`make test-fast`・`make check` の対象に含める。
sandbox 側のディレクトリと、その中のテストのディレクトリには `__init__.py` を置く。

型検査は pyrefly の `search-path` に `sandbox` を加え、`layer_inspector` を import 名で
解決する。

## 背景

layer-sweep のトピック別 nDCG@1000 は、隣接する層どうしでは相関が 0.9 を超えるのに、
層 1 と層 12 では 0.6 程度まで下がる。この相関の違いがどの文書の順位として現れて
いるのかを定性的に分析するために、本 ADR の内容を実装する。

## 理由

### 集計を結果ファイルに書き出し、表示はそれを読む

Streamlit は操作のたびにスクリプトを先頭から実行し直す。文書のキャッシュは 6.7 GB、
コレクションは 332,918 件あり、表示のたびに読むことはできない。表示に使うのは
10 トピック分の順位と数百件の文書だけであり、一度書き出しておけば、以降の起動では
GPU もモデルも要らない。

### エントリポイントを 1 つにする

集計と表示で実行する手順を分けると、結果ファイルがないままアプリを起動したときに
表示できない。アプリの起動時に結果ファイルの有無を確かめて足りなければ作る形にすれば、
使う人が覚える手順は起動の 1 つで済む。

### 切り詰めたトークン列を decode して表示する

目的は、モデルが何を見て順位を付けたかを読むことである。元の文章を表示すると、正規化で
変わった文字や `[UNK]` になった文字、512 トークンで落ちた末尾が、モデルが受け取った
ものと区別できない。decode した文字列はモデルへの入力そのものであり、これらがすべて
そのまま見える。

切り詰めはトークン単位で起こり、WordPiece のトークンは文字の途中で分かれないため、
末尾の文字が壊れることはない。切り詰められた文書は文の途中で `[SEP]` に続くため、
打ち切りの有無は表示から読み取れる。512 トークンを超える文書は、全 332,918 件のうち
5,332 件 (1.60%) である。

特殊トークンを取り除くと `[UNK]` も消え、語彙にない文字があったこと自体が見えなくなる。

### 両方の層の順位を並べる

浅い層と深い層で何が違うかを読むには、同じ文書が反対側の層で何位だったかが手がかりに
なる。反対側の層の順位は、トピックの選択に使った 2 つの層で検索し直す時点で得られて
いる。

### 画面を 2 分割にする

文書を読む領域を広く取るため。一覧は幅が狭くても読めるが、文書は幅と高さがないと
読みにくい。

### 依存とテストをプロジェクトと同じ環境で扱う

dependency group に入れれば、パッケージ本体の依存を増やさずに済む。`make sync` と
Dockerfile は `uv sync --all-groups` で同期するため、ローカルでもコンテナでも追加の手順は
要らない。pyrefly はリポジトリ内の `*.py` をすべて型検査するため、streamlit はどのみち
プロジェクトの仮想環境から解決できる必要がある。

テストの実行を `tests` と揃えれば、ビューアのテストだけが実行されずに壊れたまま残る
ことがない。`tests` には `__init__.py` がなく、テストファイルは名前だけで import される。
sandbox 側をパッケージにしておけば、同じ名前のテストファイルがあってもパッケージ名つきで
import され、衝突しない。

pytest はテストのディレクトリから `sandbox` を import の探索先に加えるため、
`layer_inspector` を import できる。一方 pyrefly は `sandbox` を探索先に持たず、
`missing-import` になる。`search-path` を足さないと、テストは通るのに型検査だけが落ちる。

### 適合文書の上位と下位を重ならないように分ける

全 83 トピックのうち、コーパスに存在する適合文書が 10 件以下のものは 14 トピックある
(最少は 5 件)。現在のモデルで選ばれる 10 トピックでは最少が 10 件で重なりは起きないが、
モデルを変えると選ばれるトピックが変わる。上位と下位の表に同じ文書が出ると、下位の表が
「取り落とした適合文書」を表さなくなる。

## 採用しなかったもの

- **起動のたびにキャッシュから順位を計算する。** キャッシュを `st.cache_resource` で
  一度だけ読む形でも、起動のたびに 6.7 GB の読み込みと GPU が要る。表示する設定は
  ほぼ固定であり、毎回計算し直す理由がない
- **集計と表示でエントリポイントを分ける。** 実行する手順が 2 つになり、結果ファイルが
  ないまま起動すると表示できない
- **元の文章を表示し、512 トークンを超えた部分を灰色にする。** 正規化と `[UNK]` の違いは
  見えないままである。また対象モデルのトークナイザは文字位置との対応を返せず、境目は
  先頭から切った文字列をトークナイズし直して探すことになる。200 件で試したところ
  2 件は境目までのトークン列が全文のものと一致せず、境目は近似にとどまる
- **特殊トークンを取り除いて decode する。** `[UNK]` が消え、語彙にない文字があった
  ことが見えなくなる
- **トピックの DESCRIPTION を表示する。** 検索には題名だけを使っており (ADR-0011)、
  モデルが見ていないテキストを並べると読み違える
- **上位と下位に分けず、適合文書が 10 件以下なら 1 つの表にまとめる。** 表の意味が
  トピックによって変わる
- **画面を左・中央・右の 3 分割にする。** 文書を読む領域が狭くなる

## 結果

- 結果ファイルがない状態での起動だけは、キャッシュの読み込みと GPU が要り、表示までに
  時間がかかる
- 結果ファイルがある限り、表示はそのファイルを作った時点の記録とキャッシュに基づく。
  記録やキャッシュを作り直したときは、結果ファイルも作り直す必要がある
- 表示される文書は単語ごとに空白で区切られ、元の文章より読みにくい
